Роли и этапы:

Telegram Bot Service:

Принимает запрос от WebApp с initData.

Не занимается валидацией. Его задача — передать initData и информацию о запрошенном пользователем действии (command или callback_data) дальше в систему.

Выступает как клиент API Gateway. Отправляет HTTP-запрос (например, POST /api/v1/auth/telegram) с телом, содержащим initData.

API Gateway:

Единая точка входа. Все внешние запросы идут через него.

Маршрутизация: На этапе аутентификации (первый запрос с initData) он проксирует запрос в identity-service.

Аутентификация для последующих запросов: После успешной аутентификации клиент (Telegram Bot Service или WebApp) будет прикладывать JWT-токен в заголовке Authorization: Bearer <token>. API Gateway должен проверять валидность этого токена (подпись, срок) перед тем, как пропустить запрос к защищенным сервисам. Это можно делать путем запроса к identity-service (эндпоинт /validate) или, что эффективнее, самостоятельно проверять подпись, если у Gateway есть публичный ключ (публичная часть ключа, которым identity-service подписывает токены). Второй вариант снимает нагрузку с Identity Service.

После проверки JWT, Gateway маршрутизирует запрос в целевой сервис (orchestrator, file-storage-service, ai-service).

Identity Service:

Принимает от Gateway запрос на аутентификацию по Telegram (/auth/telegram).

Валидирует initData с помощью bot token.

Извлекает telegram_id.

Ищет пользователя в БД по telegram_id. Если не находит — создает нового (возможно, запрашивая минимальные данные из initData).

Генерирует пару JWT (access, refresh) для этого пользователя, сохраняет хэш refresh-токена в БД.

Возвращает токены в ответе Gateway.

Orchestrator Service:

Получает запросы от API Gateway только с валидным JWT-токеном в заголовке.

В заголовке JWT содержится userId. Orchestrator использует его для привязки задач (генерация документа) к пользователю.

Orchestrator координирует работу других сервисов (template-service, ai-service), выступая для них как внутренний клиент. Внутренние сервисы могут также проверять JWT или, что проще, доверять исходящим от Orchestrator запросам (если сеть изолирована). Для большей безопасности можно использовать service-to-service аутентификацию (например, с помощью отдельных сертификатов или API-ключей).

Протокол: Для синхронных запросов — HTTP/REST (как в ваших OpenAPI-схемах). Для длительных асинхронных задач (генерация документа) можно использовать брокер сообщений (RabbitMQ, Kafka), где Orchestrator публикует задачу, а другие сервисы подписываются на соответствующие очереди.

3) Системная аналитика для этапа аутентификации через Telegram Bot
Цель: Безопасно идентифицировать пользователя Telegram в системе и выдать ему внутренние учетные данные (JWT) для доступа к защищенным функциям.

Предусловия:

Пользователь запустил бота в Telegram и нажал кнопку, открывающую WebApp (например, "Консультация с AI").

У бэкенд-сервисов (telegram-bot-service, identity-service) есть доступ к BOT_TOKEN.

Основной поток событий:

Инициирование аутентификации:

Клиент (Telegram WebApp) отправляет initData на telegram-bot-service.

Передача данных в шлюз:

Telegram-bot-service формирует HTTP-запрос к API Gateway на эндпоинт /api/v1/auth/telegram, включая initData в тело запроса.

Маршрутизация на Identity Service:

API Gateway распознает путь аутентификации и перенаправляет запрос в identity-service.

Валидация данных Telegram:

Identity-service получает initData и BOT_TOKEN.

Сервис проверяет hash в initData для подтверждения целостности и подлинности данных. Если проверка не пройдена — поток завершается с ошибкой 401 Unauthorized.

Извлечение идентификатора:

Из валидированных данных извлекается telegram_id пользователя.

Поиск/Создание пользователя:

Identity-service выполняет запрос в БД пользователей по telegram_id.

Альтернатива А (Пользователь найден): Получает существующую запись.

Альтернатива Б (Пользователь не найден): Создает новую запись пользователя, используя данные из initData (first_name, last_name, username). Присваивает роль USER.

Генерация токенов:

Для пользователя генерируется пара JWT-токенов:

Access Token: Краткосрочный (например, 15-60 минут), содержит userId, role.

Refresh Token: Долгосрочный (например, 7 дней), сохраняется в виде хэша в БД, связанным с пользователем.

Ответ:

Identity-service возвращает API Gateway объект с access и refresh токенами.

Установка учетных данных:

API Gateway передает ответ обратно в telegram-bot-service.

Telegram-bot-service устанавливает токены в httpOnly, Secure, SameSite=Strict куки для домена вашего бэкенда ИЛИ возвращает их в теле ответа WebApp для хранения на клиенте.

Завершение:

Пользователь аутентифицирован. Последующие запросы от его имени будут содержать JWT-токен, который API Gateway будет проверять перед доступом к orchestrator, file-storage и другим сервисам.

Post-conditions: Пользователь получил валидные JWT-токены, ассоциированные с его telegram_id в системе. Сессия создана.
